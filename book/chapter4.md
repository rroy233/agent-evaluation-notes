# 第 4 章 组织测评集并解读实验结果

前三章的产出连起来已经可以跑出分数：成功标准定义了要什么，任务规格固定了怎么测，判定器给出了结论。但一个分数本身还不能回答“这个版本能不能发布”。

要从测评分数走到发布判断，还需要解决三个问题。

- 第一是**可比性**：一次版本比较要固定哪些条件，分数变化才能归因到候选版本本身。
- 第二是**随机性**：Agent 的执行存在随机性，单次结果不足以代表稳定表现，需要通过重复试验和相应指标进行描述。
- 第三是**个案复核**：汇总分数会掩盖具体任务上的新增失败，因此最终判断还需要回到任务和执行记录。

这三层解决的是离线测评能够观察到的问题。测评集尚未覆盖、只在线上真实使用中暴露出来的问题，留到第 5 章讨论。

## 4.1 测评集与实验

**测评集（`Evaluation Suite`）**是为测量特定能力或行为而组织的一组任务，它表达测量目的[1]。**数据集（`Dataset`）**是任务输入、可选预期结果和元数据的存储载体[3][4]。两者职责不同：测评集回答“我要测什么”，数据集回答“这些任务的数据存在哪里、怎么改”。同一个测评集可以落在一个数据集上，也可以分散在多个数据集里。

本文用“测评集”指代测量目的，用“数据集”指代可版本化的任务数据。这个区分在后面的实验控制中会显出作用：测量目的靠文档和约定固定，具体任务数据则靠数据集版本固定。

**实验（`Experiment`）**是在固定配置下，让一个 Agent 版本执行测评集并接受判定器评分的过程[4]。**一次实验运行（`Experiment Run`）**覆盖选定的全部数据项。运行过程中，每个数据项产生一条执行记录和对应输出；挂上判定器以后，这些执行结果进一步转化为评分结果[4]。

![实验流程。左侧数据集里的每个输入项送入中间的 Task，由外部代码或提示词循环处理生成输出；右侧 Results 收集每项输出，再由 Evaluation Method 按代码评分、模型判定或人工评分给出对应的 Score](images/experiment-flow.jpg)

图注：数据集提供输入，Task 产生输出，判定方法再把输入输出对变成分数。图片来自 [4]。

这些对象串起来形成一条完整的实验链路：**测评集确定测量范围，数据集版本固定实际使用的任务，实验运行产生执行证据，判定器再根据这些证据生成评分。** 后面的实验控制，就是为了保证基线（`Baseline`）和候选版本经过的是同一条测量链路，使最终得到的分数能够直接比较。

## 4.2 测评集的组织

第 2 章解决了单个测评任务怎样设计。多个任务组成测评集以后，需要进一步考虑集合本身怎样组织：**这组任务承担什么作用、从哪些层面观察 Agent，以及放在一起以后是否覆盖了真正需要关注的能力和风险。**

这三个问题分别对应测评集的**用途、测量范围和任务覆盖**。一组任务可以同时承担回归保护和端到端测评，另一组任务也可以针对某项新能力，在具体过程环节上进行测量。组织测评集的目的，是让不同任务各自承担明确的测量作用，并共同形成足够完整的覆盖。

### 4.2.1 用途

一个测评集首先要明确**用它观察什么阶段的问题**。在 Agent 的迭代过程中，通常同时需要两类集合：一类用于探索尚未稳定具备的能力，另一类用于保护已经验证过的能力[1]。

**能力测评集（Capability Eval）**关注 Agent 当前还不能稳定完成的困难任务。它回答的是“这个 Agent 还有哪些能力需要继续提升”。因此，这类集合在建立时通常应留有明显的改进空间；如果所有任务都已经稳定通过，它就很难继续反映后续能力提升[1]。

**回归测评集（Regression Eval）**关注 Agent 是否仍然能够完成已经验证过的任务。它回答的是“以前已经会做的事情，现在还能不能稳定做到”。这类任务的预期通过率通常较高，一旦原本稳定通过的任务开始失败，就说明已有能力可能发生了退化[1]。

两者不是永久分开的。一个能力任务经过持续优化后，如果已经能够稳定完成，它继续作为能力信号的价值会降低，此时可以转入回归测评集。它所承担的作用随之从“判断能不能做到”变成“保护已经做到的能力”[1]。与此同时，能力测评集还需要继续加入新的困难任务，否则随着旧任务逐渐饱和，它将无法继续指出下一步的改进方向[1]。

实际迭代中，两类集合通常需要同时运行。模型、提示词、工具或工作流的修改可能提升某项新能力，也可能影响其他已经稳定的行为。能力测评负责观察改进是否发生，回归测评则负责检查这种改进有没有以已有能力退化为代价[1]。

### 4.2.2 测量范围

确定测评集的用途以后，还需要决定**从哪些层面观察 Agent 的表现**。通常需要同时保留端到端结果和关键过程两种视角[2]。

**端到端测评**站在用户目标和最终结果的角度，关注一次完整任务有没有真正完成。例如，用户要求退款时，最终是否产生了正确的退款结果；用户要求生成文件时，目标文件是否真正生成。它直接反映 Agent 对外提供的整体能力，因此通常是判断系统整体表现最重要的信号之一[2]。

端到端结果的局限是定位能力较弱。假设一组任务的成功率从 68% 降到 55%，这个变化能够说明完整任务变差了，却不能单独说明问题发生在检索、规划、工具调用还是结果生成。

因此，还需要用**过程测评**观察执行链路中的关键环节，例如检索是否得到正确信息、工具是否被正确调用、参数是否正确，或者某个子任务是否完成[2]。如果端到端结果下降，同时某个关键环节的成功率也明显下降，就可以进一步缩小问题范围。

两种视角之间还有一条重要的反向关系：**如果已有过程指标都保持稳定，而端到端结果却出现下降，就说明当前过程测评可能还存在覆盖盲区**[2]。

> 例如，一个退款 Agent 的身份验证、用户确认和退款工具调用成功率都没有变化，但整体退款成功率明显降低。检查新增失败后发现，Agent 经常在包含多件商品的订单中选择错误的退款对象，而现有过程测评并没有检查这一环节。此时应把这种新失败沉淀为新的过程测评，而不是继续只观察原来的几个指标。

因此，端到端测评主要负责发现**整体表现是否出现异常**，过程测评则帮助解释**异常发生在哪里**[2]。缺少前者，团队可能只看到各个已知模块都正常，却不知道最终用户任务已经失败；缺少后者，则可能知道任务变差了，却无法定位应该检查哪个环节。

过程测评的粒度也不需要一开始就拆得很细。可以先围绕端到端任务和少数核心模块建立集合，当实际实验出现“知道整体变差，却仍然无法定位原因”的情况时，再继续向下拆分。例如，可以逐渐形成知识库、检索、工具调用等更具体的过程测评集[2]。分层服务于诊断，而不是为了预先建立一套复杂的分类体系。



### 4.2.3 任务构成与覆盖

建立初始测评集时，不需要先追求很大的题量。可以优先纳入开发和上线前反复人工检查的核心行为、真实使用中已经出现的失败，以及影响较大的任务[1]。早期用一组规模较小、目标明确的任务就能够形成有效反馈，再随着开发和真实使用中暴露的新问题逐步扩充[1][6]。因此，任务数量本身不是目标，关键是当前最重要的能力和风险有没有进入集合。

测评集还需要保持**行为覆盖的平衡**。对于同一种行为，既要有应该发生的情况，也要有不应该发生的情况。只覆盖一个方向，会使测评长期只奖励一种行为，最终推动 Agent 朝这个方向过度优化[1][6]。例如，一个用于观察搜索行为的集合如果只包含“应该搜索”的任务，Agent 可能通过更加频繁地搜索获得更高分，却在本来不需要搜索的问题上产生新的问题。集合中同时保留正反两侧的任务，才能区分“正确触发”和“无条件触发”[1]。

任务的**来源也应当具有一定多样性**。生产数据、历史记录、领域人员整理的数据和合成数据都可以进入测评集[5]。真实数据能够反映已经发生的使用情况，人工整理和合成数据则可以补充低频但重要、或者尚未在线上出现的场景。这里关心的是不同来源共同形成的覆盖范围，而不是原始数据怎样加工成一个完整的测评任务。

除了来源，还需要检查**场景分布**。测评集不能长期只由正常路径上的简单任务组成，还应覆盖典型情况、边界情况和对抗性情况[5]。这些场景共同决定测评集能否暴露系统在复杂输入和异常条件下的问题。这里同样只关注集合层面是否存在空缺，具体边界任务和对抗任务怎样设计已经属于第 2 章的任务设计范围。

测评集的覆盖也不是一次确定后就保持不变。Agent 的能力、产品功能和用户使用方式都会变化，新的失败模式也会不断出现。开发和生产中发现的真实失败，应逐步沉淀进相应的能力集、回归集或过程测评集，使已经发现的问题能够在后续版本中持续受到检查[1][5][6]。

因此，组织测评集最终要形成一种互补关系：**能力测评指出下一步需要提升什么，回归测评保护已经具备的能力；端到端测评观察完整任务是否成功，过程测评帮助定位失败环节；任务覆盖则保证这些集合没有长期遗漏重要行为和风险。** 后续实验比较建立在这些已经组织好的测评集之上。

## 4.3 实验控制

版本比较要尽量只改变待评估的 Agent，其他会影响结果的条件保持一致。只有控制住这些变量，基线与候选版本之间的分数差异才有可能归因到本次变更[2][7]。

实验控制主要涉及三件事：**固定比较条件、保证执行环境一致，以及完整记录每次运行**。前两者保证实验具有可比性，实验记录则保证结果能够复查和追溯。

### 4.3.1 固定配置

每次用于版本比较的实验，都需要固定并记录会影响结果的配置。至少包括四组：

- **任务配置**：数据集版本和任务标识；
- **Agent 配置**：提交版本、模型、提示词、工具和运行参数；
- **判定配置**：判定器定义、评分规则和判定器版本；
- **运行配置**：执行环境及其数据、依赖版本，以及试验次数、并发和超时等设置[3][7]。

固定这些配置的目的，是让基线和候选面对相同的任务、评分标准和运行条件。否则，分数变化中可能同时混入任务、判定器或环境本身的变化，无法判断差异究竟来自 Agent 还是实验条件。

其中，数据集需要特别进行版本管理。测评集会持续加入新任务、修改已有任务或归档过时条目，因此不同时间看到的“当前数据集”可能已经不是同一批数据。数据集版本记录每次新增、修改、删除或归档，可以按指定时间点取回当时的条目集合[3]。

图注：每次条目变更都会生成新版本，按时间点可取回当时的条目集合。图片来自 [3]。

这条机制解决的是一个很实际的问题：测评集是活的，团队会不断往里加任务、改预期结果、归档过时条目。如果比较两个版本时用的是“当前最新”的数据集，那么两次实验用的其实不是同一批任务，分数差异里就混进了任务本身的变化。记下版本时间戳，取回的就是同一批数据，历史实验才可复现[3]。

固定数据集版本只解决数据一致，它消除不了 Agent 输出的随机性。因此还有一条硬要求：基线和候选必须使用同一数据集版本和同一套判定器定义，直接比较才成立[3][7]。

### 4.3.2 执行环境

执行环境要接近生产，并且为每次试验提供干净、相互隔离的初始状态[1][2]。

环境是最容易被破坏的那一项。典型破坏方式是执行环境与生产不一致：测试环境调用的下游接口数据和生产不同，或者沙箱里没有预置用户的历史文件，导致 Agent 拿不到必要上下文[2]。这类差异的危害不在分数偏高或偏低，而在让离线分数和线上表现系统性偏离。后果比一次测错更严重：团队会逐渐不再信任离线测评，转而依赖临场判断[2]。

隔离不足另有一层危害。残留文件、缓存数据和共享资源会引入与 Agent 能力无关的失败，让多个本应独立的试验因为同一个基础设施原因一起失败；它也可能反向虚增通过率[1]。

环境保真度有一个可操作的检验方法：拿同一批样本，分别在离线环境和线上影子流量里各跑一遍，看两边结论是否一致。差异过大就说明保真度不够[2]。这个检验同时覆盖了“环境是否像生产”和“环境是否稳定”两个问题。

环境数据和业务规则发生变化后，要重新确认任务是否仍可完成、判定器是否仍有效，并记录新的环境版本[1][2]。环境变更为什么必须当作版本事件，理由和数据集一样：它会让此前所有结论的适用前提失效，而且这种失效是静默的，旧分数不会自己变红。

### 4.3.3 实验记录

实验记录至少要关联五项内容：<u>数据项</u>、<u>执行记录</u>、<u>最终状态</u>、<u>各项评分</u>，以及 <u>Agent 配置和成本、延迟等运行信息</u>。成本记录一次运行消耗的资源，延迟记录从任务启动到完成的耗时[4][7]。

实验记录最终要支持一条完整的追溯路径：

> **汇总结果 → 具体任务 → 具体试验 → 执行证据与评分依据**

如果一项汇总分数发生变化，应当能够沿着这条路径找到对应的任务和执行记录。这样，后面的版本比较不仅能看到“分数变了”，还能够进一步检查变化发生在哪些任务、由什么执行结果造成。

## 4.4 重复试验与汇总指标

重复试验（`Trial`）是同一任务在相同配置下的一次独立执行[1][2]。需要它的原因很直接：Agent 输出带随机性，单次通过或失败不足以代表任务的稳定表现。

选择指标之前要先分清两个问题。第一个是“一个任务跑很多次，怎么描述它的表现”，这由单任务成功率回答。第二个是“整个测评集汇总成一个什么数字”，`pass@k` 和 `pass^k` 的分歧就在这里。两者容易混用，但回答的问题相反。

单任务成功率是同一任务在多次试验中通过次数占试验次数的比例。它的适用范围只到单个任务，用来识别不稳定或特别困难的具体任务，不能代表整个测评集的水平。

- `pass^1`（等于 `pass@1`）是每个任务只看一次试验是否成功，再在测评集上汇总。它用来比较一次尝试的平均任务成功水平，是 `k = 1` 时的基准指标，说明不了多次执行的一致性。

- `pass@k` 是对每个任务运行 k 次，至少有一次成功的概率，再对任务汇总。它适用于允许多次尝试、且任意一个可用结果就满足需求的场景。k 增大时这个指标通常上升，因为它描述的是“多试几次能不能撞上一次成功”[1]。

- `pass^k` 是对每个任务运行 k 次，全部成功的概率，再对任务汇总。它适用于面向用户、每次都应稳定完成的任务。k 增大时这个指标通常下降，因为它描述的是可靠性和一致性[1]。同一个语义任务在多次试验中能否保持一致，就是用这个指标表达的[8]。

两个指标指向相反，所以**指标选择要服从产品要求，不能看哪个数字好看**。允许候选方案或重试的任务关注 `pass@k`，因为多试几次得到可用结果就是可接受的；一次失败就会影响用户的任务关注 `pass^k`，因为用户不会给第二次机会[1][8]。选错指标会把结论引向反面：一个用 `pass@k` 衡量很漂亮的版本，在 `pass^k` 下可能远达不到面向用户的要求。

这里有一处实现上的限制。按数据项组织的实验通常假定每个数据项只跑一次，也就是默认没有重复试验[4]。要得到 k 次试验，实际做法是让同一批数据项跑 k 轮，或者把重复放在实验之外的运行环节，再把结果按任务聚合。指标的计算方式不变，但记录结构必须能区分同一任务的不同试验，否则聚合时无法还原每个任务的成功次数。

## 4.5 版本比较与结果复核

版本比较以**经过审阅的发布版本**为基线，以**待评估版本**为候选[7]。比较前需要确认两者使用相同的数据集版本、判定器定义和必需任务集，并记录对应的 Agent 与判定器版本。前文已经讨论了这些条件为什么需要固定，这里只在可比的实验之间进行结果比较。

版本比较最终形成的是两层判断：**汇总指标回答整体发生了什么变化，个案复核回答这些变化为什么发生。** 两者结合以后，才能判断一次分数变化究竟代表真实的能力提升或退化，还是来自实验条件和判定器本身。

### 4.5.1 汇总结果

版本比较首先看整体结果，例如任务通过率、各类评分、成本和延迟[7][9]。这些汇总指标能够快速反映候选版本整体上变好了还是变差了，但不能代替逐项检查。

第一，**整体分数相同，不代表具体任务没有发生变化**。平均值会把不同任务上的提升和退化相互抵消。例如，基线和候选版本的整体准确率都为 50%，逐项比较后却可能发现：候选修复了“促销商品退款”的失败，同时让原本可以正确处理的“标准退款政策”发生退化[7]。两边通过的任务数量相同，但产品含义完全不同。因此，除了整体指标，还需要检查哪些任务从通过变成失败，以及哪些任务从失败变成通过。

第二，检查**结果是否完整**。缺失任务、任务执行失败和判定器没有返回结果，都不能直接按照通过处理[7][9]。这几种情况都意味着实验结果不完整；如果在汇总时直接忽略，整体指标可能因为缺少失败信息而被抬高。

第三，检查**评分是否可信**。即使判定器已经返回了分数，也需要把评分说明和实际输出放在一起检查，确认评分结果能够由执行证据支持[7]。如果分数变化来自判定器异常，而不是 Agent 表现变化，就不能直接用于版本判断。

### 4.5.2 个案复核

个案复核则用于解释这些变化为什么发生。重点应放在新增失败、关键任务退化，以及评分异常的样本上。

第一步是打开对应的执行记录和 Trace，检查输入、工具调用、中间状态、最终输出以及各项评分[7]。这样可以从汇总分数重新回到原始证据，判断失败发生在哪个环节。

第二步是区分失败的性质。至少要把三种情况分开：**Agent 执行失败、任务或环境本身存在问题，以及判定器误判**[1][7]。例如，一个合理的改写没有通过字符串匹配，可能说明判定器过于僵硬；而一段表面流畅的回答如果包含没有依据的说法，则仍然属于 Agent 本身的失败[7]。复核的目的就是避免把这些情况混在同一个“失败”标签里。

如果问题来自任务、环境或判定器，应先修正相应的评测条件，再重新运行受到影响的样本。特别是修改判定器以后，不能只重新评估候选版本；基线和候选都需要使用新的判定器重新评分，否则两边的结果仍然来自不同标准，不能直接比较[7]。



## 4.6 发布门槛

发布门槛（`Release Policy`）是**把实验结果映射成发布或阻断决定的规则**。它需要在解释候选版本结果之前确定，并与测评集中不同任务的重要程度对应[7][9]。如果先看到候选结果再决定门槛，判断标准就可能随着当前版本的表现发生变化。

发布门槛通常由两类基础规则构成，并可以组合使用[9]。

- 第一类是**必过门槛**。指定的关键任务或关键评分必须全部达到要求，只要其中一项失败，就阻断发布。它适合安全、合规、数据准确性和不可逆操作等不能由其他高分抵消的要求。

- 第二类是**回归门槛**。已经在批准基线中通过的任务，在候选版本中也必须继续保持通过[9]。它保护已经验证过的能力，允许候选版本增加新的能力，但不能让已有能力发生退化。

实际发布通常会同时使用两类规则，并结合整体指标设置阈值[9]。例如，关键任务既要求全部通过，又要求批准基线中的已有能力不发生回归；在此基础上，还可以要求整体任务成功率、成本或延迟达到预设范围。

不同指标还可以进一步按照重要程度分层。安全和数据准确性等检查项可以作为一票否决项；体验类或加分项则可以设置整体阈值[2]。这里改变的是**发布判断规则**，并不改变前面单个任务本身的评分方式。

发布门槛要真正用于版本管理，还需要两个配套机制。

- 第一是**批准基线**。它记录已经经过人工审阅并接受的 Agent 版本，以及对应的数据集版本、判定器版本和各任务结论[7][9]。候选版本即使通过当前发布检查，也不能自动成为新的批准基线。新的基线应由一次完整运行产生，并经过人工审阅和正常的代码评审流程后再更新[9]。这样做是为了避免把候选版本中的已知失败自动吸收到基线中。一旦某个失败随着基线更新被默认接受，后续版本比较就可能不再把它识别为新增退化[9]。

- 第二是**流程接入**。把发布门槛接入持续集成与持续交付（`CI/CD`）或正式发布流程以后，离线测评才能在每次变更时稳定执行[2][9]。没有进入发布流程的门槛，本质上仍然只是一条建议。

至此，离线测评形成了一条完整链路：**测评集定义要观察什么，实验保证不同版本可以比较，版本复核解释变化来自哪里，发布门槛再把这些结果转换成明确的发布决策。** 第 5 章继续处理离线测评之外的问题，也就是 Agent 上线以后在真实使用中出现的新行为和新失败。
