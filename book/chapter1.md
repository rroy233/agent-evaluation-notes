# 第 1 章 Agent 的成功标准

判断一个 Agent 做得好不好，靠的是一套事先写清、事后可查的条件。

这套条件必须回答三个问题。第一个是量什么：Agent 系统的哪些部分参与本次测评。第二个是凭什么量：一次执行能留下哪些证据。第三个是算不算成功：在什么条件下判定任务达成目标，以及要不要要求它每次都达成。三个问题回答完，团队才有条件把标准写成任务。

这份文档是下一步的直接输入：它决定了要写哪些测评任务，也决定了判定器要检查什么。

## 1.1 Agent 测评的对象

### 1.1.1 Agent 的任务执行

Agent 的执行路径不固定，这一点把它和普通模型调用区分开。工作流把多个模型调用按开发者排好的步骤串起来，每一步的输入输出都在安排之中；Agent 面对的是没有固定解法的任务，它带着一组指令和工具，在每一步自行决定是调用工具还是回复用户[1]。

工具是开发者定义的一段代码，模型可以执行它。这段代码可以是一个辅助函数，也可以是对现有服务的应用程序编程接口（`API`）调用，例如 `check_order_status(order_id)` 接收订单号，调用接口返回状态[1]。工具按后果分两类：一类只读，调用完环境不变；一类会写，调用一次环境就与调用前不同。写接口让工具调用带上了外部后果，测评因此必须回到环境去看结果。

环境状态在 Agent 视野之外。数据库里的内容只能通过接口读写，Agent 看不到数据库本身，看到的只是接口返回的结果；接口在数据库上执行的动作是确定的[2]。这一点直接决定判定怎么取证据：任务成功不能靠 Agent 的自述，要回到环境去看它到底改成了什么样。

Agent 同时对着两个通道工作。它既通过接口操作数据库，也和模拟用户对话，两个通道各有自己的动作空间，Agent 可以调用工具，也可以发出任意自然语言消息[2]。两个通道互不可见：模拟用户只看到自己与 Agent 的对话，看不到 Agent 与接口之间的交互记录[2]。这条信息隔离决定了测评要收集两类记录，一类是接口调用，一类是对话。

这么一来，同一个用户目标就可能对应好几条合格路径。航空客服场景里有一个例子：用户想把最近的预订改到同一天飞旧金山，而这张票是基础经济舱。政策规定基础经济舱不能改签，但 24 小时内可以取消。Agent 的做法是先查到舱位，拒绝改签，再提出取消并重新预订[2]。这条路径由多轮对话推出，不是预先编排的动作序列。测评因此不能拿执行路径去比对标准答案。

### 1.1.2 Agent 系统的测评范围

测评覆盖的是系统，不是模型。评测一个 Agent 时，实际评的是运行框架和模型共同工作的结果。运行框架负责处理输入、编排工具调用和返回结果，模型只是框架里的一个部件[3]。换成工程视角，模型进入真实系统之后，会和提示词、技能、工具链、记忆、状态管理和业务流程耦合在一起。测评要回答的是这个组合能不能稳定交付结果。测评对象因此是一个整体，由模型、系统、工具和流程组成[4]。

区分模型测评和 Agent 测评，是因为两者的结论用途不同。常被统称为测评的东西其实分三类：用来横向比较模型能力的行业基准，例如 MMLU 一类的榜单；ROUGE、BERTScore 这类通用数值指标；以及为自己业务实现的具体测试[8]。本文讨论的是第三类。前两类的结论只说明模型本身处在什么水平，没有覆盖业务实际使用的工具、领域规则和运行环境，因此不足以支撑发布判断。

用通用指标代替业务测评是明确的错误做法，具体表现为只依赖困惑度或 BLEU 一类的学术指标，以及构造不能真实反映生产流量分布的测评数据[8]。两种做法都在回避同一个问题：真正需要验证的东西不容易计算，于是团队换成了一个容易计算的东西。

测评的目的有两个层次。第一层回答 Agent 好不好，给出判断；第二层回答哪里好、哪里不好，指明迭代方向[4]。只回答第一层的测评无法支持改进，团队知道分数降了，却不知道该让谁去修什么。

失败样本能把这两个层次的差别显示清楚。对 115 条零售客服轨迹的人工检查发现，其中 40 条失败。4 条失败源于用户指令的笔误或歧义，随后修正；剩下 36 条属于 Agent 自身问题，归成四类：错误决策占 33.3%，信息错误占 25.0%，参数错误占 22.2%，复合请求只完成一部分占 19.4%[2]。这些比例本身不是发布依据，它们的用途是分派责任：参数错误指向信息抽取，复合请求只完成一部分指向长上下文和记忆，两处要改的地方完全不同。

测评还要回答值不值得。一个可以引用的成本口径是：在零售客服场景里把函数调用 Agent 与模拟用户配对，Agent 侧每个任务花费 0.38 美元，模拟用户侧 0.23 美元，每个任务跑一次试次总计约 200 美元；其中 Agent 侧的开销有 95.9% 来自输入提示词，长系统提示词是成本主体[2]。这组数字说明效率条件不是附加项，成本直接由固定输入和固定工具决定，改变它们就会改变测评本身。

## 1.2 测评证据

一次测评留下两类东西：测试本身怎么组织，以及执行过程留下了什么。前者是任务、试次和测评集，后者是执行记录和最终状态。判定规则只能读取它们，不能读取别处。

### 1.2.1 任务、试次与测评集

任务（`Task`）是一次测试，它有明确的输入和成功标准[3]。Agent 领域借用了大模型评测里的“问题、参考答案、评价标准”三元组，三元组的每一行都可以看做一个 Task[5]。任务的关键要求是结果唯一。构题时反复修改用户指令，用函数调用 Agent 试跑并检查轨迹，直到确认在领域政策下不会出现第二种结果[2]。唯一性决定了判定能否自动化：指令留有歧义时，测评结果就变成噪声，团队无法分辨分数变化来自 Agent 还是来自题面。

试次（`Trial`）是同一个任务的一次运行。模型输出在多次运行之间会变化，所以单个任务通常要跑多个试次，结论才稳定[3]。试次数量决定结论能说明什么：确认单个任务的成功率需要每个任务 40 次以上试次，而主结果表格中每个任务至少跑 3 次[2]。两类数量服务于不同目的，前者用于校验题目本身，后者用于比较方案。

归拢一批任务的标准是要考察的能力或行为，这样的一组任务称为测评集（`Evaluation Suite`），同一批任务通常服务于一个宽泛目标，例如客服测评集同时覆盖退款、取消和升级[3]。从资产角度看，测评集还可以按用途分成三类：黄金集定义好的下限，错题集记录踩过的坑，挑战集标定能力的边界。三类集合的价值都落在可回归上，每一个曾经犯过的错都不应该再犯第二次[5]。

能力集和回归集的验收标准相反。能力集在起步阶段的通过率应该偏低，它瞄准 Agent 目前做不好的任务，给团队一个需要爬的坡；回归集的通过率应该接近 100%，它防止改动引起倒退，分数下滑就意味着有东西坏了[3]。两类集合混在一起会让结论无法解释：整体通过率上升，可能只是回归集里漏进了简单任务，而不是能力真的提升了。

### 1.2.2 执行记录与最终状态

执行记录（`Trace`，也叫 `Transcript` 或 `Trajectory`）把一次试次里发生的事情全部记下来，包括输出、工具调用、推理过程、中间结果和其他交互。在接口层面，它就是测评结束时那份完整的 messages 数组，每一次调用和每一个返回都在里面[3]。

最终状态（`Outcome`）指试次跑完后环境变成了什么样。一个订票 Agent 可能在记录末尾说“航班已预订”，而最终状态要看环境数据库里是否真的存在这条预订[3]。

记录过程有工程上的理由。如果日志里只有“用户说了什么”和“最后回复了什么”，团队几乎无法判断根因。一次执行要经过意图理解、任务规划、工具调用、环境交互、中间结果处理和策略调整，这么多环节里任何一层出问题，最终效果都会变差[6]。执行记录的作用是把这些环节白盒化，记录所有影响模型输出的输入信息[6]。观测基建的底线是“最小可归因”：至少拿到完整的模型调用输入输出和技能调用记录，能凭记录复现一个坏案例发生了什么[6]。

执行记录也是判断策略调整的证据。失败分析发现，Agent 会漏掉对话开头明确提出的请求，也会漏掉隐含动作。后者有一个例子：用户要求修正所有订单里的错误地址，Agent 只检查了一个订单就停下[2]。最终状态能显示结果不对，只有执行记录能显示它停在了哪一步。

这些证据由两类运行框架生产。Agent 运行框架（`Agent Harness`，也叫 `Scaffold`）的作用是让模型能以 Agent 的方式工作，处理输入、编排工具调用并返回结果；评估一个 Agent 时，实际上评估的是运行框架和模型的组合[3]。测评运行框架（`Evaluation Harness`）管的是整条测评流程，包括准备指令和工具、并发跑任务、记录全部步骤、评分并汇总结果[3]。

### 1.2.3 Run、Trace 与 Thread

一次测评覆盖多长的执行范围，要在设计任务时定下来。Agent 的执行可以拆成三层，每层对应一个观测粒度：`Run` 指一次模型调用或工具调用，`Trace` 指一轮 Agent 执行的完整过程，`Thread` 指由多个 `Trace` 组成的多轮会话[7]。

单步执行适合检查局部决策。工具是否选对、参数是否传对，这两个问题都能在一步之内回答。把 Agent 循环约束成只走一步，就能隔离出单个动作，再对工具选择、参数或中间输出做断言。约一半的 Agent 测试用例放在这一层，原因是快、便宜，而且给出的是针对具体决策的信号，不是笼统的好坏[7]。

完整回合适合在发布前做整体检查，它同时看三样东西：最终回复是否正确，执行路径是否合理，状态变更产生的产物或副作用是否正确。日程安排类任务的一个例子是同时断言三件事：Agent 修改了正确的文档、最终消息确认了更新、文件里确实写进了新偏好。三件事可以用不同的判断器分别检查[7]。

多轮会话适合检查跨轮能力，例如意图切换、记忆管理和跨轮的多步推理。一个在单轮上表现良好的 Agent，仍可能在这些方面出问题。会话级测评在整段对话结束后评三件事：用户真正想做什么，任务有没有完成、没完成是为什么，以及包含工具调用和决策的完整交互过程[7]。单轮分数不能替代会话级结论，因为一个 Agent 可以在 90% 的单轮上得分良好，却没有在整段对话里解决用户的问题[7]。

三层粒度是配合关系。完整回合和多轮会话说明 Agent 有没有坏，单步执行说明坏在哪一步，可靠的测评集需要同时保留整体视角和局部视角[7]。失败归因给的比例能说明问题集中在参数还是决策，但要定位到具体哪一步，只能回到单步粒度。

`Trace` 这个词在两类来源里范围不同，用时需要区分。一类用法指一次试次的完整记录，等同于 `Transcript` 或 `Trajectory`[3]。另一类用法指一轮 Agent 执行，范围可能小于整个任务[7]。本笔记在需要区分单回合与多轮会话时采用后者的 Run、Trace 和 Thread 范围，讨论记录内容时采用前者的用法。测评任务必须写明它覆盖一轮执行还是整个任务，否则不同批次的统计范围会不一致。

## 1.3 成功条件

成功标准是一组可检查的条件，用来判断一次任务是否达成目标。条件从用户要完成的任务和业务必须遵守的规则推导出来，通用文本相似度最多只能作为其中一项检查[8]。

### 1.3.1 用户目标与业务目标

用户目标是用户本人想拿到的东西，业务目标则是产品方想通过这个任务拿到的东西。这两者都不能直接当判定条件。

判定条件不能停在这两类目标上，因为业务结果和模型能力分处两端，中间存在天然鸿沟，无法直接映射，必须补一层面向任务系统的桥梁指标[4]。用 AI 搜索可以看清这三层：业务侧关心 DAU、留存和点击，搜索系统关心召回率和点击率，Agent 层关心的则是意图识别是否准确、检索是否有效、结果整合是否可信[4]。只有把三层串起来，团队才能回答业务指标为什么变差，以及模型能力提升为什么没有变成业务收益[4]。

Agent 层的成功条件就是那层桥梁，它把这两类目标落成可以检查的任务事实，例如意图是否识别正确、该查的信息有没有查、该改的状态有没有改对。这一层是测评真正要写的东西，用户目标和业务目标的作用是决定这些事实的取舍。这类事实可以归成四类。建立这层指标需要懂业务流程的人参与，跨层解释不是靠指标名称自动成立的[4]。

写的时候顺序不能颠倒：先写用户目标，再写业务规则和风险限制，最后才写条件。反过来做会有一个可观察的后果，团队照着手上已有的指标去编目标，测出来的分数无法解释业务变化。

任务本身还要反映真实使用分布，测评应当说明模型在真实世界分布中的能力，并同时覆盖典型场景、边缘场景和对抗场景[8]。这条要求有一个具体后果：只用典型任务，团队会把 Agent 优化成只会处理典型输入的 Agent。构题时同时锁定用户身份、意图和偏好，可以让政策下的结果保持唯一，这与反映真实分布并不冲突[2]。

### 1.3.2 单次任务的成功条件

单次任务的成功条件分四类，合起来覆盖结果、过程、效率和风险四层。这四类只是一个任务在四个角度上的检查点：任务完成条件看结果，规则与安全条件看风险，过程质量条件看过程，效率条件看开销。

任务完成条件检查最终回复或最终状态是否满足用户目标。最终状态可以直接验证时，优先检查它。一种具体实现把奖励定义为动作分与输出分之积：动作分取决于最终数据库是否等于唯一的目标数据库，输出分取决于 Agent 的回复是否包含必要信息。以退货任务为例，Agent 与用户的对话可以千变万化，读操作调用哪些也不限，只要唯一的写操作是规定的退货调用，并且回复里出现了 `54.04` 和 `41.64` 两个金额，奖励就记为 1[2]。这个设计把怎么走交给 Agent 自由决定，把走到哪固定下来。

规则与安全条件检查 Agent 的操作是否遵守权限、领域政策和操作限制。规则条件不能省，一个直接理由是奖励为 1 只是任务成功的必要条件，并非充分条件：Agent 可能在没有得到用户明确确认的情况下就发起退货，此时数据库状态正确，却已经违反了政策[2]。状态比对覆盖不到这类错误，说明它不能作为唯一检查。

领域政策（也就是业务规则）有两种执行方式，对测评的要求不同。一部分政策由接口自身实现，例如使用不在用户资料里的支付 ID 会直接返回错误，环境会自动挡住这类违规。另一部分只能靠 Agent 自觉，例如航空政策规定不同会员等级和舱位对应不同的行李额度，而系统不会替 Agent 填对行李件数[2]。第二种情况无法用状态比对兜底，只能通过执行记录检查。

一条规则条件是否真的在起筛选作用，可以用消融实验检验。把领域政策从系统提示词里移除后重测，规则偏常识的零售客服场景中，`gpt-4o` 的 `pass^1` 只下降 4.4%，说明它此前的成功大多来自直觉式的工具使用，并没有真正依赖政策文档；而在行李额度随会员等级和舱位变化的航空场景中，移除政策让 `gpt-4o` 下降 22.4%，`gpt-3.5-turbo` 只下降 1.2%[2]。同一项条件在规则复杂度不同的场景里效果相差很大，所以要分场景测，把两边的分数混在一起会掩盖差异。

过程质量条件检查执行记录里的行为，例如是否收集了必要信息、是否用工具处理了关键事实、是否交代了处理结果。它只看行为与正确性、安全性或用户体验有没有关系，覆盖的正是结果层看不见的部分。过程层关注规划是否合理、步骤是否稳定[4]。对话式 Agent 的交互质量本身就是被测对象，成功是多维的：工单是否解决属于状态检查，是否在 10 轮内完成属于执行记录约束，语气是否合适属于评分规则，三者可以分别检查[3]。

过程检查的边界在于不预设路径。断言 Agent 按特定顺序调用工具看起来很严格，实际会把测试做得过于脆弱，因为 Agent 经常走出设计者没有预料到、但同样有效的路径[7]。可行的做法是检查产出结果和产生结果的决策质量，路径与预期不同时允许按进展给部分分；只有顺序本身就是正确性或安全性的要求时，才做严格的有序匹配[7]。

效率条件检查任务有没有在可接受的时间和成本内完成，可用的指标包括耗时、Token 消耗和工具调用次数，对话轮次也是常见的一种[4]。这类条件必须写出阈值或比较对象，否则无法判定。阈值的来源可以是任务本身设定的动作上限：每个任务的 Agent 动作数上限是 30 步，超过即停止[2]。上限决定了什么算做完，也决定了长任务和短任务的成功率能否放在一起比较。

四类条件合起来覆盖结果、过程、效率和风险四层[4]。之所以四层都要，是因为两个 Agent 可能最终都做对了，但一个路径清晰、工具调用稳定、耗时可控、可以重复复现，另一个反复试错、路径混乱、靠偶然命中结果、不可复现。只看最终答案会把两者判成同一水平，而从规模化、成本优化和用户体验的角度看差别很大[4]。条件不是越多越好，一个任务只保留会影响发布判断的那些。

### 1.3.3 可靠性

Agent 的行为在多次运行之间会变化，因此单次成功不能代表稳定交付。这种变化的实际表现是每个任务各有自己的成功率，一个任务可能 90%，另一个可能 50%，同一任务这次通过下次不一定通过[3]。变化有明确的来源：任务、用户提示词和数据库转移都保持不变，只有用户和 Agent 消息的语言采样在变，于是对话过程不同，任务的目标状态相同[2]。

可靠性指 Agent 在多次试次里都能满足成功条件。这些试次语义相同，关键环境条件也一致。换成统计说法，就是在 k 次独立同分布试次中保持一致和稳健[2]。

两个指标从不同方向度量它。`pass@k` 是一个任务跑 k 次独立试次，至少成功一次的概率。`pass^k` 是跑 k 次独立试次全部成功的概率[2]。计算方式是按任务取平均，任务跑 n 次成功 c 次时，两者都有对应的无偏估计[2]。`pass@k` 衡量多试几次能不能撞上一次成功，`pass^k` 衡量连续 k 次是否都不出错。

两个指标的走势相反。`pass@k` 随 k 增大而上升，因为尝试次数越多，至少命中一次的机会越大；`pass^k` 随 k 增大而下降，因为要求每次都成功会越来越难[3]。用同一个单次成功率可以推出差距：单次成功率 75% 的 Agent 连续三次全部成功的概率是 0.75 的三次方，约 42%[3]。实测落差更大，函数调用 Agent 的平均任务成功率超过 60%，而 `pass^8` 降到 25% 以下[2]。

选择哪个指标取决于产品预期。一次成功即产生价值的任务适合用 `pass@k`，例如代码生成，多提几个方案、有一个能跑通就有意义。用户期望每次都要成功的任务适合用 `pass^k`，例如客服[3]。

`pass^8` 低于 25% 这组数字说明可靠性为什么必须进入成功标准，而不能停在参考指标的位置。平均成功率超过 60% 的 Agent 在用户眼里并不可靠，因为用户每一次提出的都是同一种请求，期望得到的也是同一种结果。这种差距把改进方向指了出来：下一步要提的是稳定性和规则遵循能力，而不是平均成功率[2]。

判断哪些任务需要可靠性要求，可以看用户是否会重复提出同类请求。这类任务的成功标准必须包含可靠性的产品要求，并写明要求的试次次数和通过方式。可靠性本身也要有度量办法，测评系统需要保证准确、性能和可靠性，用来应对 AI 系统的非确定性输出[8]。提出要求的同时要给出校准视角：同一批样本由不同的人、不同时间或机器测量，结果应当一致；量具本身也需要随业务扩量定期校准[5]。

## 1.4 成功标准文档

前面的结论可以收成一页文档。这一页固定判定所依据的对象和条件，不展开测评任务的细节。这样处理有两个理由。条件需要有共同依据，两位领域专家读到同一份任务时，才可能独立给出相同的通过结论[3]。条件也需要有出处，判定结果每一次追溯，都要落到某个写下来的要求上。

这一页至少包含五栏。

- 测评对象的范围：模型、提示词、工具、运行框架和环境里，哪些部分属于本次测评。
- 用户目标和相关业务规则，包括必须遵守的领域政策和风险限制。
- 单次任务要检查的完成、规则与安全、过程质量和效率条件。
- 是否需要检查跨试次可靠性，以及可靠性的产品要求。
- 每项条件需要的证据：最终回复、执行记录、最终状态或运行数据。

栏目之间的依赖是单向的。用户目标和业务规则决定保留哪些条件，条件决定需要哪些证据，证据又决定要为任务准备什么输入和环境。判定只读取这一页声明过的证据，没有声明的证据不进入判定，因此遗漏证据的后果是判定无法执行，而不是判定放松要求。

写不出来的一栏不能先用占位结论填上。缺条件意味着这个任务无法写出成功标准，缺证据意味着它无从检查。这两种缺口都应该在转入任务设计之前暴露出来。

第 2 章把这一页转换成可重复执行的测评任务。
