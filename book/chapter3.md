# 第 3 章 判定器设计

任务规格里写清了预期结果、行为约束和要留下的证据。接下来要定的是：谁来读这些证据，凭什么说这次执行算通过。

判定器（`Grader`，也叫 `Evaluator`）就是承担这项工作的逻辑：它依据评分规则评估 Agent 某一方面的表现，读取任务规格里的证据并输出判定结果[1][4]。一个任务通常要配多个判定器，因为一个任务可能同时要求最终状态正确、关键动作发生、回复说清楚，这几件事没法用一套逻辑一起判[1]。

判定器和任务规格是一一对应的关系。任务规格用预期结果和行为约束提出要求，判定器负责检查这些要求有没有被满足。判定器读的证据必须先声明，原因在于声明过的证据是它唯一的输入，它不能检查自己读不到的东西。

判定器要解决的核心问题是可信。可信有两层含义：规则本身说得清楚，以及判定者与领域人员对同一份证据得出一致结论。“好不好”本身是主观问题。实践中真正的困难有两个：不同的人评得不一样，机器和人评得也不一样[13]。所有取舍都服务于这两层，也就是让同一份证据稳定地得出同一个结论。

判定器最终落成一份判定器规格，用于在固定条件下比较 Agent 版本。

## 3.1 判定对象与结果

判定器有两个必须先定的东西：它检查什么，以及它输出什么。

### 3.1.1 判定对象

判定对象是判定器要读的那部分材料[1]。Agent 执行会留下两样东西：环境最终变成了什么样，以及整段执行的过程记录。后者又可以只看整体，也可以只看其中某一次操作。再加上 Agent 给用户的最终回复，判定对象一共四种。

这四种对象承担不同的检查任务。最终状态适合验证可以查证的事实，例如订单状态、数据库记录、生成的文件和测试结果。一个典型的例子是确认订单是否真的写入后台，而不只是确认页面上出现了成功提示[1]。执行记录适合检查那些不会体现在最终状态里的行为，例如用了哪些工具、有没有越权、信息收集是否完整、关键决策是否合理。最终回复适合检查用户拿到的信息、表达质量和行动说明。

同一份证据可以支撑多个判定器。这也给任务设计提出了一个反向要求：每新增一条检查，先确认对应的证据已经收上来了，否则这条检查落不了地[1][3]。

### 3.1.2 判定结果

判定结果（`Score`）是对一个判定对象作出的质量记录。它有一个名字、一个取值和一个数据类型，另外可以附一段说明[6]。结果要挂在执行证据上才读得到，通常挂在一次端到端交互上，也可以挂到更细的一次操作，或者挂到一整段多轮会话上[7]。

四种结果形式的选择，取决于这个分数接下来要拿去做什么。两个问题就能定下来：这个判断能不能汇总和比较，以及质量是不是一个连续的程度。

先问能不能汇总。如果这个判断本质上是一段只有人能读的说明，那就用文本结果。文本结果的定位很明确：它面向开放式记录，写评审意见或判定理由，典型用途是先做开放式记录，再在此基础上归纳成可量化的评分项[6]。代价是它不能参与汇总，因为自由文本无法有效聚合和比较，所以它不进入实验对比、大语言模型（`LLM`）判定和分数分析这三处[6]。把文本结果和其余三种放在一起合算总分，是常见的误用。

能汇总之后，再问质量是离散的还是连续的。有两个确定取值就用布尔结果，例如输出里有没有违规内容、格式是否合法；候选结论能事先穷举就用类别结果，例如正确、部分正确、错误；质量是一段连续程度就用数值结果，例如相关度分数或准确率[6]。

数值结果最容易出错，因为它自带一种虚假的精确。用的时候必须交代三件事：取值区间、哪个方向更好、每个区间怎么解释。缺了这三件，同一个数字在不同人那里读出不同含义。相邻分数之间的主观差异还会额外引入噪声，所以能二元化时优先二元化[12]。

结果还要能长期跟踪。这就引出一个单独的对象：评分配置。它把分数的名称、数据类型和取值范围固定下来，让同一类分数在整个团队里保持同一套结构[7]。没有这一步，同一个名字的分数在不同批次里可能取值不同、解释不同，跨版本比较就失去意义。评分记录与协作会再次用到这个对象。

每条结果另外带有来源标记，说明它由应用程序编程接口（`API`）、自动判定还是人工标注产生[7]。来源之所以要留，是因为不同来源的可信度不同：自动判定的结果需要校准，人工标注的结果需要检查一致性。

单个判定器的输出到此确定。一个任务通常挂多个判定器，它们的输出怎么合成一个结论，由合成规则决定。

## 3.2 评估方法框架

评估方法是从执行证据产生评分结果的方式。参考材料把模型判定、代码判定、人工评分和分数接入都列为评估方法[2]。放在一起看，它们其实回答三个不同的问题。谁以什么机制作出判断，这决定判定的能力和成本，是判定机制。判断时拿什么当参照，这决定判定是否公平，是判定参照。结果怎么记录、由谁协作完成，这是评分记录与协作。把这三层分开看，同一套评分规则就可以换不同的执行者，而不必重写规则。

### 3.2.1 判定机制

判定机制是直接产生评分结果的主体和逻辑，它回答三层里的第一层。四种机制的差别集中在三处：能处理什么类型的判断，能不能给出解释，以及跑一次要多少成本。

代码判定执行确定性的程序检查，输出通过、数值或其他预先定义的结果[3]。它适合可以直接验证的事实，例如精确匹配、格式校验、结构验证、工具调用检查和自定义业务规则。代码判定不涉及采样，因此结果可重复，也容易调试。它的代价是僵硬：检查固定措辞会把本来有效的表达判为失败，检查非必要的调用顺序会把有效执行判为失败[1]。

大语言模型判定（`LLM-as-a-Judge`，以下称 LLM 判定）让模型根据输入、输出、评分规则和可选的参考答案给出评分与判定理由[4]。它的强项是开放式语义条件，例如完整性、依据质量、沟通方式和执行过程是否合理。它也能输出书面理由，这一点在排查分歧时很有用。它的代价是不确定和偏置：输出长度会影响打分，候选项的顺序会影响选择，换一个判定模型或改一次提示词都可能改变结果[11][12]。这类判定必须用人工标签校准之后才能作为发布依据[11]。

Jev 判定（`Jev-as-a-Judge`）把数据组装成一份状态，连同预先定义的类型化问题一起发给决策模型，模型返回带概率的类型化答案[5]。它不生成文本，这是它和 LLM 判定的根本区别：没有生成步骤，也就没有生成带来的不确定性。它在一次调用里回答多个问题，因此成本低、延迟低，适合在大量样本上做分类、评级和是否判断。

它的限制同样明显。它不输出理由，判定错了只能回头检查状态和问题定义。它不能弃权，所以分类问题必须自己留好“其他”或“不确定”这类出口，否则它会挑一个最不离谱的选项[5]。状态也要精简，塞进与问题无关的材料会降低准确率[5]。这项能力目前仍是实验性的[5]。

人工评审由领域人员根据评分规则检查执行证据，给出评分和意见[8]。它能处理复杂的领域判断，也能形成参考标签。它的成本最高、速度最慢，评审者之间还会产生分歧。它因此主要用在三处：高风险决策、规则尚未明确的案例，以及校准自动判定器[12][8]。

### 3.2.2 判定参照

判定参照是判定器比较证据时采用的标准。它与判定机制是两回事：同一套评分规则，可以交给代码执行，也可以交给大语言模型或人工执行[4][5]。

第一种参照是评分规则，也就是用明确的通过、失败或等级条件直接判断输出。它适合没有唯一标准答案、或者需要同时检查多项质量要求的任务。规则必须写得具体，含糊的要求要拆成原子项，否则执行规则的人或模型只能凭感觉补全。

第二种参照是参考答案，也就是把输出与预期结果或标准答案比较[11]。它提供明确的锚点，代价是难以覆盖所有同样有效的表达和执行路径。

第三种参照是成对比较，也就是在同一评分规则下比较两个候选输出，选出较好的一个[11]。它适合版本选择或方案比较，只需要知道相对优劣的场景。它给出的是相对结论，不能单独说明任何一个候选是否达到发布标准。成对比较比绝对打分更可靠，因为语言模型在两两比较上比在开放生成上更稳定[11][12]。

三种参照可以组合使用。Jev 的类型化问题是评分规则的一个极端形式：全部候选答案和等级都必须在调用之前定义好，模型只负责从中选一个并给出概率[5][4]。

### 3.2.3 评分记录与协作

评分记录与协作负责把结果写进执行记录，并组织人工或外部系统参与。它回答三层里的第三层。这一层不改变评分规则，但决定三件事：团队事后能不能找到这个分数，能不能拿它和其他分数比较，能不能追溯它是怎么来的。

三种方式的差别，可以用一个问题区分：分数是谁算出来的，以及算出来之后要不要人来接手。

手工评分和标注队列都属于人来给分，区别在批量。手工评分适合少量样本的快速复核、单个问题排查和建立人工基线，启动成本低，一次处理一个样本[9]。标注队列解决的是同一件事的规模问题：把一批执行记录编入队列，由领域人员按统一的评分配置批量标注[8]。标注队列有一个前提：它必须绑定一套评分配置，也就是一套事先定好的评分项。没有这个绑定，评审者只能各自定义标准，队列产出的标签就不具备可比性[8]。

`API` 或软件开发工具包（`SDK`）写分数属于机器给分，适合已有自定义评估流程的团队，或者需要把外部系统的结果汇入同一个分析面的场景[10]。这一层的边界在于：接入方式本身不提供任何判定逻辑，它只负责把分数写进来。分数背后的计算过程是否正确，仍然要靠校准来验证。

这里出现一个反馈关系。标注队列的产出有两个去向：一是直接当作参考标签，二是用来校准自动判定器。校准的价值在于它能把人工判断放大：一旦自动判定器与人工标签达到可接受的一致程度，后续就可以只让机器跑，人工只处理机器标记出来的样本[8]。所以人工标注的投入不是一次性的，它换来的是后续判定成本的下降。这也解释了为什么人工评审在这个体系里的定位是校准而不是主力。

要让这条路径走得通，人工分数和自动分数必须能对上。把两者写进同一条执行记录里，才能计算一致程度、找出分歧样本，并据此修改判定规则[8]。这一步在实现上依赖评分配置：人工标注和自动判定只要共用同一个评分配置，两者的结果就是同构的，可以直接比较。

## 3.3 方法选择与组合

方法选择要从成功条件、证据类型和所需结果倒推，不能凭习惯。每种机制各有能力边界，把它对应到条件上，选择顺序大致如下。

能从环境状态、工具参数或测试结果直接查证的条件，交给代码判定。这类条件可以写成确定规则，反复运行也不会变形，是所有条件里最省事的一类。

候选标签、等级或是否判断事先已经定好，而且样本量很大时，交给 Jev 判定。类型化问题能在一次调用里批量回答，还能返回概率供后续设阈值。

需要判断完整性、依据质量或沟通质量，并且希望看到书面理由的，交给 LLM 判定。它能依据评分规则理解开放式语义条件，代价是需要人工标签校准。

依赖专业知识、风险偏高，或者自动判定还没和领域判断吻合的，交给人工评审。人工标签在这里同时提供两样东西：领域基线和校准依据。

分数已经由应用、流水线或持续集成（`CI`）作业算好的，通过 `API` 或 `SDK` 写进同一条执行记录，让它和其余结果放在一起比较。

一个任务配多个判定器时，可以把它们按证据类型分工。可验证事实交给代码判定，类型化的线上信号交给 Jev 判定，开放式语义质量交给 LLM 判定，高价值样本由人工评审建立参考标签[1][5][8]。一种常见的组合实践是：每个样本都跑一遍便宜的类型化判定，再对其中一部分样本或标记出来的样本补一次 LLM 判定，人工标签则用来检查前两种判定的结果是否可信[5]。这样安排的理由是人工评审最贵，把它用在验证机器判定上，比让它承担全部判定更划算。

## 3.4 评分规则

评分规则（`Rubric`）是一组明确说明判定依据的检查项。它的作用是把抽象的成功条件变成可以判断的事实或标准[13][1]。

### 3.4.1 评分项

一条评分项只负责一个事实或一个判断，比如有没有做身份验证，或者有没有说清退款金额[1]。写的时候要交代四件事：判什么、看哪份证据、什么算过、什么算不过。

证据不够时，评分项应当返回未知。未知的含义是现有材料既不足以判过、也不足以判不过，它和失败是两回事[1]。给出未知这个出口还有一个实际作用：可以反过来检查规则本身。未知的比例偏高，通常说明规则写得不够清楚，或者证据采集得不够全[13]。

开放式质量要求必须拆成具体的评分项。把“这个回答好不好”下钻成一组可以用是或否回答的检查项，主观的模糊感受就转成了可判断的事实依据，人与人之间、人与机器之间的分歧随之下降[13]。评分项的结果可以用布尔、类别或数值，但粒度越清楚，人工评审和自动判定越容易得出可比较的结论[13][1]。

### 3.4.2 任务结论

任务结论由多个评分项合成。合成规则不是自由选择，它由评分项之间的关系决定。

关键的一步是分清这些评分项测的是同一件事的不同侧面，还是互不相干的不同要求。同一件事的侧面可以加权累加，例如一份报告在覆盖度、准确性和结构上各占多少分，最后算总分。互不相干的要求不能简单累加，因为它们的失败后果不对称：退款流程少做一步是体验问题，跳过身份验证是安全违规，两者的严重程度不可比。把后者放进加权总分，等于允许用前面几项的高分把它买通。

由此得到三种合成方式。必过规则要求所有关键评分项通过，适合安全、合规和不可逆操作，因为这些地方一条不过就应当否掉整个任务。加权规则给评分项分配权重，用总分与阈值决定结论，适合允许不同程度完成的任务。混合规则同时保留两者，例如任务必须先满足权限限制，再按完整性和效率比较质量。

合成时还要保留部分得分。一个正确识别了问题、也验证了客户身份、只是没能完成退款的 Agent，明显好过一个一开始就失败的 Agent，两者的结果应当能区分开[1]。这个差别的价值在诊断上：只给一个失败标记，团队不知道问题出在流程后半段还是根本没能启动；给出部分得分，改进的起点就清楚了。

最后一步是让结论落回证据。合成出来的失败必须能回到具体的评分项和具体的证据，否则团队拿到一个失败结论却无从下手。

评分规则优先检查结果和关键决策。只有正确性和安全性依赖步骤顺序时，才把工具调用顺序写进规则[1]。这条限制来自一个具体的失效教训：把固定工具序列写成要求会让测试过于脆弱，因为 Agent 经常走出设计者没有预料到、但同样有效的路径[1]。

规则本身也可能出错，而且错得很隐蔽。有一类问题是判定器要求的门槛高于题目给出的门槛，结果按题面优化的模型反而失分，忽略题面目标的模型得分更高[1]。另一类问题是判定过于僵硬，例如把 `96.12` 判为不符合 `96.124991…`[1]。这些案例说明评分规则和题目本身要一起复核，不能只检查 Agent。

## 3.5 校准与验证

校准和验证是两件不同的事。校准用人工标注的参考样本，检查自动判定的结果是否稳定贴近领域人员的判断。验证检查判定器是否真的在测量任务规格里声明过的条件，而不是测了别的什么。两者共同决定判定结果可不可信[12][8]。

### 3.5.1 参考标注

参考标注是领域人员对一批有代表性的执行给出的判断，连同判断的理由[8]。它同时用于两个目的：检查人工评审之间的一致程度，以及衡量 LLM 判定与领域判断之间的差异[13][12]。

参考样本要覆盖四种情况：通过、失败、部分完成和证据不足。只留正向样本会让判定器只学会识别一种结局。

多位评审者必须使用同一套评分规则，并且要用背靠背的方式独立标注，不能让后标的人看到前一个人的结论。出现分歧时，处理方式有三种：修订评分项、补充示例，或者把证据要求写得更明确[13]。分歧本身是有用的信号，它通常指向规则里还没说清的地方。

这件事有一个可以量化的读数。“未知”这个结果的比例不只是判定输出，它同时反映规则的质量：未知比例偏高，通常说明这条评分项写得不够清楚，或者证据采集得不够全[13]。持续修订直到单条评分项的一致程度达到事先设定的阈值，规则才算稳定，例如把人与人之间的一致率定在 85%、人与机器之间定在 90% 这样的水平[13]。阈值要事先定，事后定就成了给结果找台阶。

### 3.5.2 判定器检查

判定器检查是在代表性样本上把自动结果和参考标注放在一起比。检查有四个层次，顺序对应四类不同的问题。

第一层，先确认判定器真的产出了结果。判定器报错或没有返回值，本身就是一种失败，不能当成“没问题”跳过[7]。这类问题在批量运行里最容易藏起来，因为它表现为分数缺失而不是分数偏低。

第二层看一致程度。LLM 判定与专家结论要有相当的一致性，才谈得上规模化[12][4]。标注样本从 20 条左右起步，之后逐步增加，避免少量样本把规则带偏[12]。这里要留意一个容易高估的数字：通用基准上语言模型判定与人工的一致率可以超过 80%，与人工标注者之间的一致率相当，但到了领域特定的 Agent 任务上，这个基线会明显下滑，所以校准必须用自己业务的标注样本，不能用通用结论代替[12]。

第三层看判定依据。审阅判定理由和相关执行记录，确认判定器真的读到了它应该读的证据。这一步要防的是判定器走了捷径：靠输出长度或格式这些与质量无关的特征得出结论[11][12]。这类捷径不会降低平均一致率，但会让判定在边界样本上系统性出错。

第四层查偏置，这里有三处已知来源。语言模型判定受输出长度影响，倾向于给更长回答更高分；候选项的顺序会影响选择；改写提示词也可能改变结果[11][12]。另一个偏差来自一次判太多：把多项要求交给同一个判定器一起判，它们之间会互相干扰，因此更稳的做法是先拆成结构化评分项，再让每一项由一个独立的判定器单独判[1]。前两处属于机制性偏差，第三处说明判定规则里任何一处措辞都不是无关紧要的。

Jev 判定另有三个检查点：问题是否原子化，也就是一个问题只包含一个判断；状态里是否只放了必要的证据；类别里是否留了不确定的出口[5]。第一条和第三条规定了问题怎么写，第二条规定了喂给判定器的材料要精简，因为与问题无关的内容会降低准确率[5]。

判定器还需要长期监控，原因和 Agent 不同。判定模型会随版本变化而漂移，同一份证据在不同时间可能得到不同结论，因此要定期重新校准[12][5]。漂移的特点是没有外部信号：分数不会跳变，只会缓慢偏移，而偏移的方向既可能是放宽也可能是收紧。

最后一条要求把判定器当作被测系统的一部分来管。Agent、业务规则或判定模型发生变化之后，都要重跑参考样本[12][5]。改判定器和改 Agent 有一个共同后果：拿新判定器评出的结果，不能和旧判定器评出的历史结果直接比较。所以修改判定器之后要重评历史样本，让比较重新建立在同一把尺子上[7]。如果跳过这一步，团队会把判定器的改动误读成 Agent 的变化。

还有一类风险。如果评分规则本身有偏差，Agent 会被优化成迎合规则，而不是解决用户问题，此时越努力优化，离真实需求越远[13]。定期检查判定器，也是在防止这件事发生。

## 3.6 判定器规格

判定器规格记录一个可以复查的判定器。它要从判定对象和证据来源写起，交代用的是哪种判定机制、哪种判定参照，并附上实际执行的载体，也就是那段检查代码、那份提示词、那组类型化问题，或者给评审者的说明。接着写评分怎么记录、由谁协作完成。然后列出评分项、每项的结果形式和合成任务结论的规则。最后留一栏写参考标注、校准结果和已知限制。

这份规格要和任务规格对得上：任务规格里声明的每一项预期结果和行为约束，都应当有判定器负责检查；判定器用到的每一项证据，都应当在任务规格里出现过。

已知限制这一栏不能空着。记录判定器在哪些情况下不可靠、校准到什么程度，解释实验结果时才不会把判定噪声当成 Agent 的变化。
