# 第 2 章 测评任务设计

一页成功标准写明了测评对象、证据和条件，但还不是一个可以运行的东西。把它落地的形式是一份描述单个测试的记录：Agent 面对什么输入、在什么环境里执行、要什么结果，以及判定时读哪些证据。

任务设计要解决的是可复现问题。同一个任务今天跑和下周跑，应该给出可比较的结论。做到这一点需要任务规格完整到可以照着重搭场景，环境每次从同一个初始状态开始，任务本身与它声称要测的场景相匹配。三项缺一项，分数变化就无法归因，团队既不能说 Agent 变好了，也不能说变差了。

任务规格里记录的结果、约束和证据是判定的直接输入；验证通过的任务则可以进入测评集。

## 2.1 任务规格

任务规格是描述单个测评任务的记录。它规定 Agent 面对什么输入、在什么环境中执行、需要达到什么结果，以及后续判定需要读取哪些证据。完整的任务规格让同一个任务能够独立地重复执行[1][2][3]。

任务规格要回答的问题是：换一个人拿着这份记录，能不能把同一个任务重搭出来。“重搭”包括三件事，准备同样的输入、初始化同样的环境、知道跑完之后去哪里读结果。三件事里有任何一件做不到，重搭出来的就是另一个任务，两次运行之间的分数差异也就无法解释。

从已有的数据结构看，这一步是必须补的。数据集条目通常由输入和期望输出组成，期望输出让同一个输入可以在多次运行之间比较，因而成为测试用例的基础[3]。这个结构足以支撑一次模型调用的测评，用在 Agent 任务上却不够：Agent 会改变环境，而输入和期望输出里都没有环境。任务规格要在数据集条目之外补上环境和判定证据。

### 2.1.1 任务规格的组成

任务规格由五块记录组成，前两块描述起点，中间两块描述目标，最后一块描述留证。

起点是任务输入和执行环境。输入记用户请求和已知上下文；环境记工具、初始状态、权限、业务规则和外部依赖。

目标是预期结果和行为约束。预期结果记任务达成后要交付的内容、环境应有的样子，或执行中必须出现的关键事实；行为约束记执行中不能越过的政策线、安全底线和操作限制。

留证是判定证据，记跑完之后需要保存的回复、工具调用记录、环境状态和运行数据。它排在最末，因为要保留什么由前面两块决定。

这五块对应到评测集的构成上，就是问题、参考答案和评价标准三者的展开：问题落在输入里，参考答案展开成预期结果和约束，评价标准落成判定证据要读的那些材料[7]。

五块之间存在依赖，这个依赖也决定了写规格的顺序：先写输入和环境，再写预期结果和约束，最后确定判定证据。前两块决定 Agent 能做什么，第三、四块规定它应该做到什么，第五块决定跑完之后能检查什么。判定证据排在最末，是因为它由前面几块推出：只有写清了预期结果和约束，才知道要保留哪些记录来验证它们。

输入这一块要包括用户的原话和环境已知的上下文。多轮任务还要带上已经发生的对话、用户是谁、有什么已知偏好，以及此前是否已经授权。这些内容在重搭时不能丢，否则 Agent 第一步就会缺信息。

环境这一块要包括接口清单和任务开始时的数据状态。接口清单除了名字和参数，还要标出哪些调用会改变数据。数据状态要写到能让另一个人重建出来的程度，例如某个订单存在、处于什么状态、属于哪个用户。权限决定 Agent 能碰哪些数据。业务流程和限制写成规则文档，其中能被接口拦住的写进接口，拦不住的写进文档。任务依赖但不自建的服务，例如支付网关或第三方接口，也要在这里记明。

预期结果这一块从三类里选：要交付给用户的关键信息、执行结束后环境应有的样子、执行中必须出现的关键动作或事实。约束这一块分四种：业务规则上的政策限制、读写范围的权限限制、不可逆操作前的确认要求，以及时间和花费一类的资源上限。这两类内容各有各的写法。

判定证据这一块要写清留给判定器的材料。取舍标准只有一条：判定时会读到的每一项证据，都必须在这里出现过。遗漏的后果是判定无从执行，而不是判定标准可以放松。

下面是一个填好的规格。用户是某零售平台的买家，想退回一只水杯并说明理由。环境提供订单查询和退货接口，订单数据库里有这个用户的订单，退款金额要按订单实付金额算。预期结果是订单状态变为退货已受理，支付记录上出现一笔对应金额的退款，回复里给出退款金额。行为约束是商品必须未使用，退款前要获得用户确认，Agent 不得改动用户的默认支付方式。判定证据是订单和支付两张表的最终状态、完整的工具调用记录，以及回复中的金额。同一份记录换一个人执行，也应该重搭出同样的场景。

## 2.2 任务输入与执行环境

任务输入提供 Agent 开始执行时可以拿到的信息，执行环境提供它可以改变的对象。两者合起来决定任务能否还原真实场景[4][1]。

### 2.2.1 任务输入

任务输入要还原的是用户在任务开始那一刻掌握的信息和授权状态。这件事听起来只是记一段话，实际有两个容易做错的地方：信息该由谁提供，以及哪些信息根本不进输入。

先看信息该由谁提供。输入里的信息有两个来源，区别在重搭时怎么准备。用户请求由用户或用户模拟器说出，表达要做什么。上下文由环境直接提供，是 Agent 一开始就能用的信息，例如一个订单号、代码库当前的状态、知识库里的内容，或者前一次工具调用返回的结果。多轮的还要补上已经发生过的对话、用户是谁、有什么偏好、此前授权到哪一步。

两条来源的边界不清，会直接改变任务难度。把所有必需信息一次性写进初始指令是一种常见做法，早期工具调用类基准普遍这样构造，用户只做一步交互，指令里就包含完成任务所需的全部信息[4]。这种做法便于构题，代价是绕开了真实场景里最难的一环：真实用户不会一次交代清楚，Agent 需要主动追问，并在动手之前拿到授权。看起来在测同一件事，实际测的能力不同。

于是多轮任务需要一个用户模拟器，由它继续和 Agent 把对话走下去。模拟器的状态由两部分组成：带任务指令的初始系统提示词，以及到目前为止的用户侧对话历史。模拟器看不到 Agent 与工具之间的交互记录[4]，这条信息不对称划定了信息流向。这条隔离决定了信息的流向：数据库里的事实只能靠 Agent 自己调工具去查，用户不会替它说出来；反过来，哪些信息可以通过对话问出来、哪些问也问不到，也由它划定。

模拟器不是必需品。只有任务要求多轮追问或确认授权时才需要写模拟规则；单轮任务直接给出完整请求即可，加上模拟器反而多引入一个变量。

再看哪些信息不进输入，这里有任务输入唯一一条硬边界：只提供生产环境中本应对 Agent 可见的信息。用于判定的预期结果和标注不进输入。

一种做法是把每个任务实例拆成两份。一份是给用户模拟器用的指令，对 Agent 隐藏；另一份记下应该发生的数据库写入，以及对用户提问的参考答案[4]。标注对 Agent 不可见，只用于驱动模拟和最终评判[4]。

这条隔离保护的是测评的有效性：标注一旦进到输入里，Agent 就能照着答案执行，测出来的分数不再说明它的决策能力。它也让任务规格里的输入部分有了一条判断标准：凡是 Agent 在生产环境里看不到的东西，都不该出现在这里。

### 2.2.2 执行环境

执行环境要解决的是 Agent 能在什么条件下工作。它要记下可用的接口、任务开始时的数据状态、Agent 能读改哪些资源、业务规则，以及依赖但不自建的服务。接口清单除了名字和参数，还要标出哪些调用会改变数据。数据状态要写到别人能重建的程度，可以是订单表、代码仓库、文件系统或用户会话。业务规则里能被接口拦住的写进接口，拦不住的写进规则文档。

这两种规则的差别可以举例说明。航空场景中，使用不在用户资料里的支付 ID 会被接口直接拒绝并返回错误；而不同会员等级和舱位对应不同行李额度这类规则，接口不会替 Agent 算好，它必须自己填入要付费的行李件数，就像真实业务里允许操作者自行判断那样[4]。前一类规则写进接口实现，后一类只能写成文档，靠 Agent 自己读懂并用上。任务规格要分别说明这两种情况，否则判定时会分不清是接口没拦住，还是 Agent 没遵守。

环境隔离要求每次试次都从一个明确的起点开始。隔离的必要性来自共享状态的连带效应。运行之间残留的文件、缓存数据或资源耗尽会让失败互相关联，此时失败的原因来自基础设施而不是 Agent 表现[1]。共享状态也会让成绩虚高。一个具体的观察是，有内部测评发现 Agent 通过查看上一次试次留下的 git 历史获得了不该有的优势[1]。更麻烦的是，多个不同试次因为同一个环境限制而失败时，它们已经不再相互独立，整批结果都不能用于衡量 Agent 表现[1]。

环境还要与生产保持同一工作方式。测评里的 Agent 和生产环境中的 Agent 应当以大致相同的方式工作，环境本身不应引入额外噪声[1]。完全复制生产不现实，一种检验方法是拿同一批样本，分别在离线环境和线上影子流量里各跑一遍，看两边结论是否一致；差异过大就说明环境保真度不够[2]。

## 2.3 预期结果与行为约束

预期结果说明任务完成后应该达到什么状态，行为约束规定 Agent 在完成任务时不能越过哪些边界。两者把抽象的成功条件写进单个任务[4][5]。

### 2.3.1 预期结果

预期结果分三类，分别对应不同的验证方式。三类不互斥，一个任务可以同时用上。

第一类是 Agent 应交付给用户的关键信息。它适合答案明确、字段固定、格式受限的任务，检查对象是回复本身。例如客服场景里，回复是否给出了退款金额，是否说明了用户接下来要做什么。

第二类是执行结束后环境应有的样子，例如订单状态、数据库记录、生成的文件或测试结果。环境状态可以验证时优先写这一类，因为它不依赖对回复措辞的判断。最终状态优先于自述，这条原则的落点就在这一类结果上。

第三类是执行中必须发生的关键动作或事实。例如是否把决策所需的信息收集齐了，是否向用户交代了处理结果。这一类填补前两类之间的空档：有些要求既不出现在回复文本里，也无法从最终状态读出来。是否在改签前查过舱位、是否在退货前确认过商品状态，都属于这一类。

三类之外，任务规格不需要记录中间步骤。同一个任务可以接受多种合理执行路径，规格只应记录真正影响任务完成的结果和行为，避免把实现者预设的中间步骤全部写成要求。只有正确性或安全性依赖步骤顺序时，才固定顺序[1]。这条限制有实际理由：把固定工具序列写成要求会让测试过于脆弱，因为 Agent 经常走出设计者没有预料到、但同样有效的路径[1]。

预期结果也不宜写成纯开放式的生成要求。需要自动评判时，让模型做判断比让它自由生成更可靠，因此应把要求收敛成可判定的形式，例如把两个选项放在一起比较、归入若干类别，或按给定标准打分[6]。这样做不影响任务本身的难度，只是把判定所需的信息提前固定下来。

### 2.3.2 行为约束

行为约束分四种，它们划定 Agent 在执行中不能越过的线。

第一种来自业务规则，例如谁有资格退款、什么条件下可以改签、能用哪些支付方式。第二种限定 Agent 的读写范围，例如它能否改动用户的默认支付方式。第三种规定哪些操作要先取得确认，涉及不可逆结果或用户权益时必须写入。第四种给出时间和成本上的上限，例如可接受的耗时、花费、工具调用次数或对话轮次。

约束必须和用户目标一起写进任务规格，不能只靠最终状态来兜。只验证最终状态会漏掉两类问题：未经授权的操作，以及违反领域规则的执行过程。但最终环境状态正确只是任务成功的必要条件。Agent 可能在没有获得用户明确确认的情况下就发起了退货，数据库最终状态完全正确，操作本身却已经违反了政策[4]。状态比对看不见这种错误，确认约束才是它的检查依据。

## 2.4 任务质量

任务质量决定测评结果能否解释 Agent 的真实表现。一个任务要成立，需要同时满足三项要求：描述清晰、能够完成、贴近真实[1][6]。

### 2.4.1 清晰性

清晰性要求题面把 Agent 需要的全部信息给足。它包含三条具体检查：描述要足够完整；每一项预期结果和约束，都能从输入、环境或公开的业务规则里推出来；判定器要检查的路径、参数、状态和限制，都在规格里写明。

第三条最容易造成误判。判定器检查的东西必须能从任务描述里读出来，否则 Agent 会因为题面没写清而失败，与它的能力无关。一个已知案例是，任务要求 Agent 写一个脚本但没有指定文件路径，而测试假定了一个特定路径，Agent 可能因此失败[1]。这种失败把规格问题写成了 Agent 失败。

清晰性的验收标准是领域专家之间的一致性：两位领域专家读同一个任务，应当各自得出相同的通过或失败结论，并且他们自己能够完成这个任务；如果做不到，任务就需要继续打磨[1]。两人结论不同，说明任务规格还有歧义。此时增加试次数量没有用，只会把噪声测得更准。

### 2.4.2 可完成性

可完成性要求一个按说明行事的 Agent，或者一位人工操作者，能够达到任务定下的成功条件。它要排除两种情况：任务本身不可解，以及预期结果与约束之间互相矛盾。

参考解是一套已知能达到任务要求的输出或执行方式，作用是证明任务可解，并验证判定器的基本配置是否正确[1]。任务写完之后先跑一遍参考解，能在投入批量实验之前发现大部分配置错误。

对要求唯一最终状态的任务，还要检查用户指令、初始数据和业务规则能否唯一确定这个结果。判断方法是找出可能影响结果的未指定项。一个具体的例子是首选支付方式：如果它没有写进指令，用户可能给出不同回答，最终数据库就会在不同试次里变成不同样子[4]。构题时的做法是先写一版指令，用它跑一遍任务并检查轨迹，再根据暴露出的歧义打磨指令，如此反复，直到确认不存在第二种结果[4]。这类未指定项属于任务缺陷，需要在验证阶段补全。

任务多次运行仍然失败时，应当先怀疑任务而不是 Agent。大量试次累积起来通过率仍是零，通常是任务本身坏了的信号，说明需要回头检查任务规格和判定要求[1]。这与前一项是一致的：既然参考解能通过，持续失败就只能说明 Agent 缺信息或环境缺条件。

### 2.4.3 真实性

真实性指任务还原了真实用户可能遇到的情形，输入、上下文和环境都要对得上。任务因此分成两类：典型任务覆盖高频目标，边界任务覆盖异常输入、互相冲突的要求和规则限制。

两个方向都要有，只测一个方向会得到单向优化的 Agent。一个具体教训来自搜索行为的设计：如果只测 Agent 该搜索时是否搜索，最后可能得到一个对几乎所有问题都去搜索的 Agent，原因是测评只在一侧给出了反馈。可行的做法是让两个方向都受到检查：既要放进应该搜索的请求，也要放进应该凭已有知识直接回答的请求[1]。这条边界的位置不容易划准，需要反复调整规则和任务才能稳定下来[1]。

任务的来源有几个：人工验收、线上真实执行记录、用户反馈，以及专家编写的场景。线上还没出现、但业务预判会出现的任务类型，可以用合成样本补上。来源会影响任务的用途，来自生产执行记录的任务天然贴近真实输入分布，专家编写的场景更容易覆盖罕见但重要的分支。

单个任务的真实性只做到来源明确、场景完整，并能代表一个需要验证的用户目标；多项任务如何共同覆盖产品范围属于编排问题[6][3]。

## 2.5 任务验证

任务验证要确认三样东西能共同支持一次公平的测试：任务规格、执行环境和预期结果。这一步发生在任务加入测评集之前，目的是在批量运行之前发现问题，而不是等结果出来再解释异常[1][4]。

验证由四步组成。

- 用参考解或人工流程跑一遍，确认任务可完成，并检查预期结果与行为约束之间没有冲突。
- 从干净的初始状态重复运行任务，检查环境隔离是否生效，并观察每次执行是否符合任务预期。
- 审阅执行记录，检查 Agent 是否获得了完成任务所需的信息，以及判定证据是否完整。
- 发现歧义、环境缺失或判定漏洞时，修改任务规格，然后重新验证。

第三步最容易被跳过，也最常发现问题。读记录能同时回答两个问题：Agent 有没有拿到足够的信息，判定需要的记录有没有完整留档。信息不足属于任务缺陷，记录不全属于观测缺陷，两者的修法不同。这一步之所以必要，还因为它能区分失败的性质：Agent 真的做错了，还是判定器拒绝了一个有效解法[1]。

四步之间是循环关系。前一轮的修改会让任务变成新任务，先前通过的验证不再有效，需要重跑。循环的出口是任务规格稳定下来：再跑一次不再引起修改。

验证通过之后，任务规格就可以进入测评集，其中的预期结果、行为约束和判定证据交给判定器读取。
